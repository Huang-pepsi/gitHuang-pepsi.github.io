解析：32位VS64位
**32/64 指的是程序运行时的虚拟地址空间宽度（CPU 一次处理地址的位数），不是 CPU 寄存器宽度那么简单，最直观的差别是内存上限、指针大小、ABI、DLL 兼容性**
1.指针大小：4 vs 8，杜绝指针大小相关硬编码
2.加载库版本，64位Windows可以跑32，32不可以跑64
3.虚拟地址分为用户态和内核态，32位系统对半分
拓展：虚拟内存的好处
1.每个进程拥有独立、隔离的地址空间（最重要）
- 进程 A 的 `0x1000` 和进程 B 的 `0x1000`，完全不是同一块物理内存；
- 进程天然隔离，一个进程野指针乱写，**不会直接篡改别的进程内存**；
- 用户态程序不能随意访问内核地址，硬件权限配合实现保护
2.物理内存 RAM 是有限的，比如机器只有 4G 内存，但 32 位进程每个都能看到 4GB 虚拟地址，64 位进程拥有 TB 级虚拟地址。
操作系统把暂时不用的内存页，换出到磁盘页面文件；需要的时候再换回来。
- 好处：可以跑**总内存需求大于物理 RAM**的多任务程序
3.内存地址重定向、程序加载简化（PE/DLL 加载）
程序编译出来的是**相对虚拟地址 RVA**，不需要绑定固定物理地址：
- DLL 可以做地址重定位（或者 ASLR 随机基址）；
- 同一份 exe 文件，可以加载到不同进程里，在物理内存放任意位置；
- 支持 DLL 共享：一份系统 DLL（如 kernel32.dll）在物理内存只存一份，多个进程虚拟地址各自映射到这同一份物理页，节省 RAM。
👉 对应你遇到的 DLL 加载、无法定位输入点、基址重定位这些底层机制。

# 链接：
## 任务：拼装所有obj+库，即输入.obj+.lib，输出exe或dll文件（windows）

## 核心：
1.	找函数实现——去obj、lib、dll中找，lib是打包好的obj集合
2.	符号解析——符号引用转为真实地址
3.	地址重定位
4.	库合并——lib或a拷贝进exe，dll只记录地址

## VS里面的链接需要：
1.	在链接器里加入附加依赖项，添加lib名称，找指定lib文件
2.	在VC++目录添加库目录，去库目录寻找lib文件

## 关于Q_DECL_EXPORT
1.	用于生成为库的项目
2.	符号的实现在 dll 里，lib 只是告诉链接器去哪个 dll 找。
3.	编译 .dll 时，把这个符号写入 .dll 的导出表 同时自动在 .lib 里记录这个符号的索引
4.	不加的话外部链接找不到

## 链接器
1.将所有必要的目标文件链接起来生成exe文件或dll文件（windows）
2.**库文件**：由多个目标文件打包而成，链接时指定，可提取所需的目标文件
3.**无法解析外部符号**：找不到包含目标变量的函数的目标文件而无法完成链接
4.**导入库**：包含函数位于dll的信息以及dll相关信息
5.**静态链接库**：直接链接到exe文件
6.**构建**：编译+链接

# 程序运行常见错误
## 无法定位程序输入点到~~~~~~
![alt text](4.png)
- 解析：
    1.通常是新exe和旧dll【dll没这个函数】或者旧exe与新dll【dll中该函数名称有改动或者删除了】。Windows 报错措辞的老毛病------显示调用的exe，其实是exe依赖的dll文件。
    2.DLL 里有这个函数，但没 __declspec(dllexport)

        → 运行时找不到

# Make起源与发展时间线
1977年
  Stuart Feldman 在贝尔实验室发明 Make
  解决一个问题：
    源文件很多时
    每次都全部重新编译太慢
    只重新编译修改过的文件

1977年  Make 诞生（贝尔实验室）
          ↓
1988年  GNU Make 出现
        成为 Linux 下的标准构建工具
          ↓
1990年代 各种 Make 变种出现
        BSD Make / nmake(微软) / pmake
        互不兼容，跨平台是噩梦
          ↓
2000年代 Autotools 出现
        ./configure && make && make install
        试图解决跨平台问题
        但配置复杂，脚本难以维护
          ↓
2000年  CMake 诞生
        KDE 桌面环境团队开发
        为了解决跨平台构建问题
          ↓
2010年代 CMake 逐渐成为主流
        各大IDE开始支持CMake
          ↓
2016年  CMake 3.x 现代化改造
        target_link_libraries 等现代写法
        成为事实标准
          ↓
现在    CMake 是C++项目构建的主流选择

# CMake基本语法
### CMakeLists.txt

cmake_minimum_required(VERSION 3.15)
project(MyApp)

## 设置C++标准
set(CMAKE_CXX_STANDARD 17)

## 找Qt库
find_package(Qt5 COMPONENTS Core Widgets REQUIRED)

## 源文件
set(SOURCES
    main.cpp
    MainWindow.cpp
    MyClass.cpp
)

## 生成可执行文件
add_executable(MyApp ${SOURCES})

## 链接库
target_link_libraries(MyApp
    Qt5::Core
    Qt5::Widgets
)

## 包含目录
target_include_directories(MyApp PRIVATE
    ${CMAKE_SOURCE_DIR}/include
)

## 小结
1.	使用CMake
    a)	CMake简介：生成构建系统的工具。将代码文件、库文件管理，自动生成库文件或者可执行文件。根据CMakeLists.txt生成实际的构建文件，然后调用g++进行编译。
    b)	静态库.a动态库.so
    c)	Cmake本身不编译，只是根据写的 CMakeLists.txt 生成 Makefile，告诉 make 该怎么编译。
    d)	make 是根据 CMakeLists.txt 里指定的文件编译，不是自动识别，make 只编译你在 add_executable 或 add_library 里明确列出的文件，目录下有其他 .cpp 文件但没加进来，就不会编译。
2.	对比qmake：
    a)	使用qmake解析pro文件生成MakeFile文件，再使用make生成可执行文件
    b)	功能围绕Qt展开+跨平台能力弱+第三方库支持少（比如gRPC在cmake封装好了的函数find_package(gRPC REQUIRED)）
    c)	用于非Qt项目，螺丝刀敲钉子——能用，但不顺手。
